# Enrichment method and limitations

The permit source is [DDOT TOPS layer 24](https://maps2.dcgis.dc.gov/dcgis/rest/services/DCGIS_APPS/DDOT_TOPS/MapServer/24). The collector selects application or issue dates in the 2026 Eastern calendar year, the two requested occupancy types and six exact `ApplicantCompany` aliases defined in `scripts/enrich_permits.py`. It retrieves all matching object IDs and all selected features, then audits entire `TrackingNumber` groups. Nonmatching members of a selected group are retained as context and prevent a complete-group claim. A separate date/type cohort supports an audit of utility-looking names outside the aliases.

For the baseline nearest-road method, at each unique point, the [DDOT LRS](https://rh.dcgis.dc.gov/dcgis/rest/services/DDOT/RoadwayBlocks/MapServer/exts/DdotLrsExtensions/getPointOnSubBlock) supplies candidates. A request for Street, Service and Ramp separately is accepted only if all three responses succeed; the Service request may return the raw type `Service Road`. Eligible types are Street, Service, Service Road and Ramp. Alleys, trails and driveways are excluded before nearest selection. `offsetInMeters` must be finite, nonnegative and at most 50. Different road names within 1 meter normally remain ambiguous. A range address can resolve a near tie only when the nearest Street has the unique exact `unitBlock` and roadway identity/type/class agree. Conventional numbered addresses with a street-name conflict remain unresolved; the baseline method does not switch to a farther road. The frozen two-case pilot decision is documented in [ANOMALY_EVIDENCE.md](ANOMALY_EVIDENCE.md) and is bound to the pilot manifest hash in `config/case_resolutions.json`.

The selected `SUBBLOCKKEY` is looked up in [Roadway SubBlock layer 162](https://maps2.dcgis.dc.gov/dcgis/rest/services/DCGIS_DATA/Transportation_WebMercator/MapServer/162). Its `FHWAFUNCTIONALCLASS` provides codes 1–7; LRS DC functional-class values are never substituted. Code 1 ranks highest. The CSV retains original attributes, geometry diagnostics, match status/reason, selected road diagnostics, location class and application aggregates. For unresolved rows, road key and distance describe a diagnostic candidate, not an accepted assignment. An application's highest class is reported only when all captured eligible locations match, `MultiAddresses` is empty and no additional out-of-filter location belongs to the captured application. Otherwise only `highest_known` is populated.

## Version 5 supplemental methods

The original frozen files remain intact. A separate snapshot retains `base_manifest.json`, copied source files with the original hashes, and `mar_evidence.json` containing timestamped raw official queries and returned address/road features. Its manifest hashes the supplementary files. The loader checks allowed source URLs, retrieval timezone, response truncation, exact raw/flattened-feature agreement and base-source hashes. Run and verify require no network calls.

Only unresolved baseline rows are eligible for supplements. A standard address of `street A AND street B` may receive `intersection_class_consensus` when both named, quadrant-qualified arms occur among the nearest-distance-plus-1 m eligible candidates, every candidate has consistent road identity/type and all share one valid FHWA class. All supporting keys are retained; unique subblock/name/type/distance fields are blank. Special boundary names, directional ramps and different-class intersections remain unresolved. The tool does not take the highest class across conflicting intersection roads.

For conventional door-number addresses, exact case/whitespace-normalized ACTIVE MAR records must agree on one nonempty key. A unique current roadway record must match the source street and the frozen roadway identity/type/class. The key must also occur in valid original LRS candidates within 50 m. This explicit `mar_address` alternative may choose a referenced same-street road farther than the nearest road, but never expands the captured 50 m set or overwrites a prior accepted match. Conflicting/inactive/missing MAR records or changed road classes preserve the unresolved result.

The supplement producer and verifier use separate decision implementations. The verifier derives expected outcomes from retained evidence and checks every supporting-key/method/provenance field; it does not call the producer. Regression tests include conflicting intersection classes, missing arms/lookups, duplicate/conflicting MAR keys, invalid types, current/frozen class drift, tampered CSV support lists and mismatched raw evidence.

The independent `verify` command reconstructs source membership, values, geometry, candidate selection, roadway lookup, class and group aggregation from retained files, and checks hashes. It establishes consistency with this policy. It cannot establish the intended work road at complex intersections or overcome source-service outages, unknown utility aliases, omitted addresses in `MultiAddresses`, or in-place source changes between retrieval calls. All unresolved locations stay visible for review. A 2026 capture before year end is necessarily year to date.
